# プロジェクト初期評価（2026-06-04）

## 総合所見

**実現可能性は高い。** フェーズ分割・人間承認ゲート・リスク管理が明確で、「週1回のスマホ確認」という運用目標と技術選定が整合している。一方で、ベース仕様と差分仕様の **データモデル・ディレクトリ名の不一致** を早い段階で一本化しないと、実装の二度手間が発生する。

## 強み

| 観点 | 評価 |
|---|---|
| 運用思想 | スプレッドシート非表示・GAS Web アプリ一本化は、スマホ運用と相性が良い |
| 段階的自動化 | フェーズ0〜6と「最小実用版」の定義があり、スコープクリープを抑えやすい |
| リスク設計 | 高リスクキーワード・注意書きテンプレ・承認必須条件が具体的 |
| セキュリティ | API キーは Properties、MCP 最小権限、Tips 公開禁止が明記されている |
| コスト意識 | Gemini Flash 系・1日生成上限・api_usage_log は現実的 |
| 開発フロー | GitHub + clasp + Cursor + Context7 の組み合わせは保守しやすい |

## 注意点・リスク

| 項目 | 内容 | 推奨対応 |
|---|---|---|
| 仕様の二重定義 | ベース: `contents` 等10シート / 差分: `products`・`drafts` 等 | **差分の正規化モデルを採用**し、ベースは概念参照に留める |
| AI プロバイダ表記 | ベースは OpenAI 例示、差分は Gemini 確定 | 実装・settings は Gemini のみに統一 |
| Tips MCP 依存 | ベースも「安定性未確認なら手動貼り付け」と記載 | フェーズ3まで Docs 出口を必ず残す |
| スコープ量 | 初期実装項目が多い（画面9種のうち4優先など） | 最小実用版の9条件に厳密に合わせて実装順を固定 |
| setupProject() | 差分で自動構築が中心 | 初回のみ・上書き禁止のテストを最初に書く |
| モデル名 | ベース settings に `gpt-5.5` 等の例 | config シートは `gemini-2.5-flash` 等、実在モデル名に合わせる |

## 推奨実装順序（差分 Phase 0〜10 に準拠）

1. clasp 雛形と `setupProject()`（Drive / Sheets / config）
2. `GeminiClient.gs` + Properties 設定手順
3. Docs 保存 + レビュー待ち一覧（Web アプリ最小）
4. 承認・修正・保留・停止 + operation_log
5. Tips MCP（下書き作成のみ、公開は手動）
6. Playwright でスマホ UI 回帰テスト
7. api_usage_log・週次レポート

## 最小実用版までの距離

ベース仕様 §32 の条件のうち、**Tips MCP は必須ではない** と明記されているため、次のマイルストーンは明確:

> ideas（または products）登録 → Gemini 生成 → Docs 保存 → Gmail 通知 → Web で承認操作 → 操作ログ

これが動けば「原稿工場＋スマホ承認」の検証が開始できる。

## 結論

プロジェクトとして **着手してよい水準** の仕様である。次のアクションは、(1) シート設計の一本化、(2) `setupProject()` と clasp の接続、(3) Gemini API の疎通テスト、の3点に絞るのがよい。
